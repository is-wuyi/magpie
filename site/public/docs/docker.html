magpie Cloud in Docker

A multi-user AI relay with email-code sign-in, user-owned keyed providers, admin-published house channels, per-model CNY pricing and a transactional prepaid wallet.

Cloud mode is not the old single-owner browser console. Agents, Sessions, Library, Memory, MCP, subscription/OAuth providers and arbitrary plugin installation are not available. PostgreSQL is required. Do not expose an older `serve` container or a `MAGPIE_WEB_KEY` admin page to users.

Start with Compose

The checkout includes compose.yaml and .env.example. Copy the example, replace every required secret, then build and start both services:

cp .env.example .env
# Edit .env: database, auth and provider-encryption keys, admin email,
# public HTTPS URL and SMTP are required.
docker compose up -d --build
docker compose ps
docker compose logs magpie

Generate independent secrets, for example openssl rand -hex 32 for MAGPIE_AUTH_SECRET and openssl rand -base64 32 for MAGPIE_CONFIG_KEY. Use a separate random POSTGRES_PASSWORD. Never commit .env.

Open MAGPIE_PUBLIC_URL. A verified address in MAGPIE_ADMIN_EMAILS becomes an administrator; every other verified registration is an ordinary user. Users can create their own keyed providers and API keys, add published house channels, recharge and inspect their balance. Administrators create house channels, add upstream key pools, set model prices and publish or take channels offline.

Required environment

VariableMeaning
MAGPIE_CLOUD=1Selects the multi-user server and removes the local management plane
MAGPIE_DATABASE_URLPostgreSQL connection URL; Compose builds it from POSTGRES_PASSWORD
MAGPIE_AUTH_SECRETAt least 32 random bytes for email-code and session HMAC keys
MAGPIE_CONFIG_KEYBase64 or hex encoding of exactly 32 bytes for provider-config AES-GCM
MAGPIE_ADMIN_EMAILSComma-separated administrator allow-list, effective only after email verification
MAGPIE_PUBLIC_URLPublic HTTPS origin, also used for payment callbacks
MAGPIE_SMTP_*SMTP host, port, credentials, sender and TLS mode used for login codes
MAGPIE_RECHARGE_PRESETSServer-owned CNY amounts; the browser cannot choose another amount

Keep these values stable across replicas and restarts. Changing MAGPIE_CONFIG_KEY makes existing provider ciphertext unreadable. Removing an administrator address does not demote an existing admin; change the user row through a controlled administrative migration instead.

Alipay and WeChat Pay

Recharge is disabled when neither provider is configured. Configure either or both; partial or invalid configuration fails startup rather than silently accepting payments.

  • Alipay: ALIPAY_APP_ID, ALIPAY_PRIVATE_KEY, ALIPAY_PUBLIC_KEY, optional ALIPAY_SELLER_ID and ALIPAY_GATEWAY_URL. The integration uses computer website payment and RSA2 asynchronous-notification verification.
  • WeChat Pay: WECHAT_APP_ID, WECHAT_MCH_ID, WECHAT_MERCHANT_SERIAL, WECHAT_PRIVATE_KEY, the 32-byte WECHAT_API_V3_KEY and WECHAT_PLATFORM_CERTIFICATES. The integration uses API v3 Native and returns a code_url for a QR code.

The callback paths are /api/payments/alipay/notify and /api/payments/wechat/notify. They must be publicly reachable over HTTPS without a login redirect. Settlement verifies signatures, merchant/app identity, order number, currency and amount. Database row locks and unique event/trade numbers prevent duplicate credits. Offline protocol tests do not replace a small real payment and callback-replay check for each merchant account.

Before opening it to users

  • Terminate HTTPS at a trusted reverse proxy. Set MAGPIE_AUTH_TRUST_PROXY_HEADERS=true only when that proxy overwrites forwarding headers. Do not publish PostgreSQL or port 3425.
  • Provider egress refuses private, loopback, link-local and metadata addresses at the socket by default. Set MAGPIE_ALLOW_PRIVATE_UPSTREAMS=1 only for operator-controlled VPC upstreams; never enable it to let a tenant reach arbitrary internal services.
  • Keep the nonroot container, database volume and encryption/auth secrets backed up. Back up PostgreSQL with point-in-time recovery; the runtime /config volume is not the financial source of truth.
  • Every house model needs an explicit current price. Unknown prices fail closed; an explicit zero price marks a free model. Price changes affect new reservations only.
  • Test two ordinary users for provider/model/usage isolation, and confirm house upstream keys never appear in API responses or logs. Loopback is not an authentication bypass in cloud mode.
  • Run real PostgreSQL concurrency and restart tests before selling balance. Verify duplicate, tampered, out-of-order and late payment callbacks. Live SMTP and merchant checks are separate release requirements.

Operations and upgrades

Migrations are numbered, transactional, checksummed and run under a PostgreSQL advisory lock. A changed applied migration, a version gap or a newer schema stops startup. Back up before upgrading, then run docker compose up -d --build. Stop with docker compose down; do not use down -v unless you intentionally mean to destroy both volumes.

GET /api/cloud/health checks the portal's database connection. The image also keeps its gateway healthcheck and graceful drain. Background jobs recover expired holds and replay payment credits left pending by a failed post-callback write. Monitor these jobs and reconcile any reservation whose settlement failed; never clear wallet or payment rows manually.

Multiple replicas may share the database and its wallet transactions, but the provider catalog and local runtime cache are process-local. Refresh or restart every replica after changing providers, grants or prices, and keep the same auth/encryption keys. A rolling deployment should run migrations from one new instance first and allow old instances to drain.
